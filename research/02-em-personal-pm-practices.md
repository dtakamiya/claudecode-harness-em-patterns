## 1. EMが Claude Code + Obsidian を「個人のOS」として運用する事例（本命）

出典: [How I Use AI as an Engineering Manager](https://mentorcruise.com/blog/how-i-use-ai-as-an-engineering-manager-8b46a/)（MentorCruise、2026年2月公開）

エンジニアリングマネージャーが Claude Code を「これまでで最もインパクトのある生産性セットアップ」と評して運用している事例。**タスク1で挙げた個別機能を、実際に統合的なワークフローへ組み上げている点が参考になる。**

### 仕組み
- Claude CodeをMCP経由で日常ツール群に接続: **Todoist（タスク）、Google Calendar（仕事・プライベート両方）、Gmail、Slack、Granola（会議メモ）、Linear（エンジニアリングのプロジェクト管理）**。
- 中核は詳細な `CLAUDE.md`。内容は「チーム構造」「タスクシステム」「働き方」「何を優先すべきか」の指示書。

### ブロッカー検知・優先順位付けの具体的な仕組み（記事の核心）
`CLAUDE.md` に基づき、Claude Codeが毎朝自動的に以下をフラグする:
1. **3日以上放置されている項目**
2. **近づいている締め切り**
3. **仕事タスクに押し出されて後回しになっている個人タスク**
4. **注目されていない成長目標（1on1で話した育成目標など）**

これはまさに本部門のタスクボードにある「パターン2: リスク・ブロッカーの早期検知」に直結する実例。

### 22個の「スキル」によるワークフロー化
- 朝の定型作業: カレンダーをスキャンし、「その日の優先度トップ3とその理由」を意見付きでまとめた文書を生成（単なるTODOリストではなく判断の理由まで書かせている点がポイント）。
- ミーティング準備: 相手の直近のLinear活動・前回のミーティングノート・関連Slackスレッドを集約し、議論すべき論点を提案。
- ノート処理: Granolaの会議録音を取り込み、構造化してアクションアイテムを抽出。

### キャプチャ→処理→表示のループ
- **キャプチャ**: Siri、Todoist、Slackの「保存」、Granolaの録音など摩擦ゼロの入り口を複数用意。
- **処理**: Claude Codeとの定型セッション中に整理・分類・ファイリング。
- **表示**: `Today.md` / `This Week.md` を自動更新し、「今何にフォーカスすべきか」を常に一箇所で見られるようにする。

### 転用時の示唆
- 本部門の「パターン1: 複数プロジェクトの進捗集約」「パターン2: リスク検知」双方に直接使える一次事例。特に「3日ルール」のようなシンプルな閾値ベースのフラグ立ては、ハーネス設計に落とし込みやすい。

## 2. Claude Academy公式ユースケース: プロジェクトステータスレポート生成

出典: [Generate project status reports](https://academy.claude.com/use-cases/generate-project-status-reports)（Anthropic公式 Academy）

EM個人という文脈そのものではないが、「報告下書き支援」パターンの手順が具体的で、個人のPM実務に直接転用できる公式リファレンス。

### 手順（6段階のうち要点）
1. **タスク定義**: 「複数ソースからプロジェクト情報を統合してトラッカーを作る」という明確な指示。取得元（Gmail/Slack/Drive等）・追跡対象項目（owner/進捗/阻害要因）・出力形式を具体的に指定する。
2. **データソース接続**: Google Workspace（Gmail・Drive・Calendar）とSlackをコネクタで接続すれば手作業のコピペが不要になる。
3. **Claudeによる統合**: 実例では147件のメール・312件のSlackメッセージから状況を抽出し、**矛盾する進捗報告（「80%完了」との自己申告 vs 実際の証跡からは45%相当）を突き合わせて調整する**、という記述がある。これは「進捗の自己申告を鵜呑みにしない」チェック機構として、本部門の設計パターンに転用価値が高い。

### 実務への転用例（記事内で言及）
- **週次レポート自動化**: Skillとして登録し「毎週金曜14時に実行」のような定期実行にできる（タスク1のRoutines/GitHub Actionsのcronと組み合わせ可能）。
- **阻害要因の深掘り**: 特定のブロッカーについて「Slack・メール・会議録の全言及箇所を抽出」と指示すればエスカレーション履歴を即座に可視化できる。
- **経営層向けサマリー**: 進捗率・リスク項目・注視対象を1ページにまとめたエグゼクティブ報告書を自動生成。

## 3. Claude Code + Obsidian の個人ナレッジシステム（PM/マネージャー転用パターンの参考）

出典: [Claude Code + Obsidian: Build a Second Brain That Actually Thinks](https://dev.to/mibii/claude-code-obsidian-build-a-second-brain-that-actually-thinks-d61)（DEV Community）

EM本人の実例ではないが、Claude Code + Obsidianで「タスク管理・週次レビュー・優先順位付け・ブロッカー検知」を行う仕組みが具体的に書かれており、上記2事例を補強する。

### コア仕組み
- 全ノートをMarkdownで永続化することで「セッションをまたいだ記憶喪失」問題を解消。毎回のゼロからの説明が不要になる。
- 朝の `/today` コマンド実行で「前日の未完了タスク自動抽出」「週間プロジェクト進捗の可視化」「当日の優先度トップ3生成」を行う。出力テンプレートは `Focus(top3)` / `Tasks(繰越+新規)` / `Notes` の3区分。
- 週次レビュー時に「完了できなかったタスク」を抽出し理由を分析、プロジェクトの停滞パターンを可視化する（＝ブロッカー検知の実装パターン）。
- 全タスク・会議メモ・調査結果をwikilinkで連携させ、「なぜこの決定をしたか」の文脈追跡を可能にしている。

### 管理層への転用ポイント（記事内の整理表を要約）
| 機能 | 管理への応用 |
|---|---|
| Daily Note | チームのデイリースタンドアップの自動サマリー生成 |
| Weekly Review | スプリント完了率・阻害要因の自動分析レポート |
| Research Workflow | 意思決定の根拠資料の自動整理・検索性向上 |
| Connection Mapping | プロジェクト間の依存関係・隠れたリスク要因の発見 |

### 実装上の注意点（記事より）
- ノート命名規則が統一されないと検索精度が落ちる。
- 深いフォルダ構造はトークン消費増加につながり効率が悪化する。
- 初期セットアップに一定のターミナルリテラシーが要る。
