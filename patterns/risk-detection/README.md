# パターン2: リスク・ブロッカーの早期検知

## 課題

複数プロジェクトを抱える EM は、個々のタスクの遅延・放置に気づくタイミングが遅れがちになる。「1週間レビュー待ちの PR」「2週間更新のない Issue」「期限が近いのに進捗のないタスク」は、能動的に探しに行かない限り見えない。EM 本人がすべてのボードを毎日目視するのは非現実的であり、気づいたときにはすでにスケジュールへの影響が出ている。

本パターンは [パターン1: 進捗集約](../personal-progress-rollup/README.md) の発展形で、「集約して見せる」から一歩進み、「閾値を超えたものだけを能動的にアラートする」ことを目的とする。

## ゴール

EM 自身のハーネスに、担当プロジェクト群の中から「放置」「遅延兆候」を定義済みのルールで検知させ、対応が必要なものだけを浮き上がらせる。ノイズを増やさず、見逃しを減らす。

## 設計方針

- **検知はルールベースを基本にする** — 「PRが N 日レビューされていない」「Issue が N 日更新されていない」「期限が過ぎている/近い」など、閾値が明確なルールを優先する。曖昧な「なんとなく怪しい」判定に頼ると誤検知が増え、アラート自体が信用されなくなる。
- **自己申告の進捗を鵜呑みにせず、証跡と突き合わせる** — Claude Academy の公式ユースケースでは、147件のメール・312件のSlackメッセージから状況を抽出した際、「80%完了」という自己申告と、実際の証跡（コミット・PR・チケット状態）から推定した約45%の実態との乖離が報告されている（出典: [Generate project status reports](https://academy.claude.com/use-cases/generate-project-status-reports)）。本パターンでも、担当者が申告した進捗率をそのまま信頼せず、リポジトリ/ボード上の一次証跡（PRのマージ状況、コミット履歴、チケットのステータス遷移）から推定した進捗と突き合わせ、乖離が大きい場合はリスクとしてフラグするルールを設ける。
- **進捗集約ステップを再利用する** — 情報収集（各プロジェクトの状態取得）はパターン1と共通化できる。本パターンは集約結果に対してルールを適用する「フィルタ層」として設計し、二重に情報を取りに行かない。
- **重要度を分けて出力する** — すべてを同じ扱いで並べると埋もれる。「今すぐ対応が要る」「様子見でよい」の最低2段階に分け、上位だけを通知、下位はサマリの末尾やログに留める。
- **誤検知の許容度を明示する** — 完璧な検知は目指さない。閾値は最初は緩めに設定し、運用しながら EM 本人がチューニングする前提で設計する（閾値も `config` に外出しし、コード変更なしで調整できるようにする）。
- **アラートは能動的にプッシュする** — 「見に行けば分かる」ではリスク検知の意味が薄い。検知した重大項目は通知チャンネル（Slack DM等）へ能動的に送る。定期サマリとは別に、閾値超過時は即時通知するパスを設ける。
- **書き込み・自動アクションは行わない** — 本パターンは検知と通知が範囲。「代わりにリマインドを送る」「自動でアサインし直す」といった書き込み系のアクションは、EM の意思決定を経ずに実行すべきでないため、明確にスコープ外とする。

## 検知ルール例

| ルール | 条件例 | 重要度 |
|---|---|---|
| レビュー放置 | PR が open のままレビュー未着手で N 日経過（例: 3日） | 高 |
| Issue 放置 | Issue が更新なしで N 日経過（例: 14日） | 中 |
| 期限超過/近接 | タスクの due date が過去、または残り48時間以内で進捗なし | 高 |
| CI 継続失敗 | 同一ブランチで CI が連続 N 回失敗（例: 3回） | 中 |
| 担当者不明 | アサインされていないまま優先度 high のタスクが N 日経過 | 中 |
| 自己申告と証跡の乖離 | 担当者の申告進捗率と、コミット/PR/チケット状態から推定した進捗率の差が N ポイント以上（例: 20pt） | 高 |

閾値（N日、連続回数など）は設定ファイルに外出しし、プロジェクトごとに上書き可能にする。

## 構成イメージ

```
personal-pm-harness/
├── config/
│   ├── projects.yaml         # パターン1と共通
│   └── risk-rules.yaml        # 検知ルールと閾値の定義（プロジェクト単位で上書き可）
├── cron/
│   └── jobs.json              # 定期スキャン + 即時通知トリガー
├── state/
│   └── known-risks.json       # 既に通知済みのリスク項目（重複通知の抑止）
└── skills/
    └── risk-detection/
        └── SKILL.md            # 検知〜通知の手順を書いたプレイブック
```

`config/risk-rules.yaml` の例:

```yaml
defaults:
  review_stale_days: 3
  issue_stale_days: 14
  ci_fail_streak: 3

overrides:
  project-a:
    review_stale_days: 1   # 対応スピードが求められるプロジェクトは閾値を厳しく
```

## 実行フロー

1. cron が定期起動し（例: 平日朝、または数時間おき）、`risk-detection` スキルを呼ぶ。
2. パターン1と同じ手順でプロジェクト群の状態を集約する（共通ステップ、再実装しない）。
3. `config/risk-rules.yaml` の閾値を各項目に適用し、条件を満たすものを抽出する。
4. `state/known-risks.json` と突合し、**新規に検知したリスクのみ**を通知する（同じ項目を毎回再通知しない）。解消された項目は state から取り除く。
5. 重要度「高」は即時通知、「中」は定期サマリ（パターン1の出力）にまとめて記載する。

## 通知フォーマット例

```
⚠️ リスク検知 2026-09-17

[高] project-a: PR #123 が3日レビュー未着手
[高] project-b: タスク「認証基盤」の期限が本日中、進捗更新なし
```

## 実例: MCP経由で日常ツールを接続した毎朝の放置/締切/後回しフラグ

あるEMが Claude Code を MCP 経由で Todoist（タスク）・Google Calendar・Gmail・Slack・Granola（会議メモ）・Linear（エンジニアリングPM）に接続し、詳細な `CLAUDE.md`（チーム構造・タスクシステム・優先順位の指示書）をもとに、毎朝自動で以下をフラグさせている（出典: [How I Use AI as an Engineering Manager](https://mentorcruise.com/blog/how-i-use-ai-as-an-engineering-manager-8b46a/)）。

1. **3日以上放置されている項目**
2. **近づいている締め切り**
3. **仕事タスクに押し出されて後回しになっている個人タスク**
4. **注目されていない成長目標（1on1で話した育成目標など）**

「3日放置」のようなシンプルな閾値ベースのフラグは、本パターンの検知ルール（前掲テーブル）にそのまま落とし込める。また4.のように「育成目標」「個人タスク」といった、コード/チケット以外のソース（1on1メモ、カレンダー）もMCP経由で接続すれば同じ検知フレームに統合できる点は、本パターンをEM個人の業務全体に拡張する際の参考になる。

## 注意点・落とし穴

- **通知疲れ（アラート疲労）** — 閾値を厳しくしすぎると通知が多発し、無視されるようになる。運用初期は緩めに始め、実際の見逃し/誤検知を見ながら調整する。
- **重複通知** — 状態を保持せずに毎回全件通知すると、同じ問題を何度も知らされてノイズになる。`known-risks.json` のような検知済み状態の記録は必須。
- **ルールの陳腐化** — プロジェクトのフェーズが変わる（例: リリース直前は許容閾値を下げたい）のに閾値が固定だと、精度が落ちる。閾値を設定ファイル化し、EM 本人が容易に調整できることを維持する。
- **検知だけで終わらせない** — アラートを出しても EM 本人が見なければ意味がない。通知先は [パターン1](../personal-progress-rollup/README.md) と同じ、EM が実際に見る場所に固定する。
