# パターン3: `/goal` によるバックログ消化・委譲フォローアップ

## 課題

[パターン1: 進捗集約](../personal-progress-rollup/README.md)と[パターン2: リスク検知](../risk-detection/README.md)は、いずれも「見せる」「アラートする」ところで止まる —— 実際に対応するのは EM 本人であり、対応自体は手作業のまま残る。

一方で EM の実務には、「対応が明確に決まっている案件を、キューが空になるまで片付けきる」という別種の作業がある。例えば以下のような、**1件1件は軽いが数が多く、後回しにされがちな**タスク群:

- ラベル付きの issue バックログを、優先度に沿って順番にコメント・アサイン・クローズしていく
- 委譲した Jira 課題のうち「担当者からの応答待ち」のものに、一定期間ごとにフォローアップコメントを入れる
- レビュー待ちで止まっている PR に、放置期間に応じたリマインドコメントを打つ

これらは毎朝の集約サマリを読んでも「対応が必要」と分かるだけで、実際に手を動かすのは EM 自身だった。ターンごとに再プロンプトして1件ずつ処理させるのは非効率で、結局まとめて後回しにされる。

## ゴール

「条件を満たすまでセッションを自動で回し続ける」`/goal` 機能を使い、EM が定義した対応ルールに沿って、Jira バックログを**無人でキューが空になるまで**処理させる。パターン1/2が「観測・検知」であるのに対し、本パターンは「委譲された作業を実際に実行し切る」ことが目的。

出典: [Keep Claude working toward a goal](https://code.claude.com/docs/en/goal)（`research/01-official-features-for-personal-pm.md` §5 に詳細）。

## 設計方針

- **完了条件は「JQLがヒットゼロになること」に落とし込む** — `/goal` の条件文には「`project = PROJA AND labels = needs-followup` がヒットしなくなるまで、各課題を1件ずつ処理する」のように、Jira の JQL 検索結果件数を終了条件として書く。曖昧な自然言語条件（「バックログを片付けて」）だけに頼ると、小型モデルによる毎ターンの判定が安定しない。
- **1ターン1件処理を徹底する** — `/goal` は各ターン終了後に完了条件を判定する仕組みのため、1ターンで複数件をまとめて処理すると進捗の可視性が落ち、エラー時の切り戻しも難しくなる。プロンプト側で「このターンでは対象課題を1件だけ選び、処理し、ラベルを外す（または状態を更新する）ところまでで終える」と明示する。
- **無限ループ防止の上限を条件文に必ず含める** — 公式ドキュメントで「N ターンで打ち切り」を条件文に含めることが推奨されている。バックログ件数から余裕を持った上限ターン数を見積もり、`または50ターンに達したら停止` のような節を必ず付ける。
- **書き込み範囲を事前にホワイトリスト化する** — 本パターンは「委譲管理」の実行部分を扱うため、パターン1/2と異なり Jira への書き込み（コメント追加・ラベル変更・アサイン変更）を伴う。無人運用でも許可プロンプトに止まらないよう、許可モードでは対象操作（`POST /rest/api/3/issue/{id}/comment` など）だけを個別に許可し、課題のクローズやステータスの大きな変更（例: Done への遷移）は対象外にする。「片付けたつもり」で意図しない状態変更をしないための線引きを崩さない。
- **エラー時の自動リトライ/一時停止に運用を委ねる** — レート制限・使用量上限・ネットワーク瞬断は `/goal` 側が自動リトライ（3回）→ 一時停止 → 使用量上限解除後に自動再開する。EM 側で個別にリトライロジックを実装する必要はない。ただし認証失効等の「直さないと直らない」エラーは goal が自動クリアされて止まるため、起動時に一度だけ疎通確認するステップを前段に挟むと無駄な失敗を減らせる。
- **`/loop`・Routines とは役割を分ける** — パターン1の「毎朝の集約」は時間駆動（`/loop`/Routines）、本パターンの「対象が尽きるまで処理」は条件駆動（`/goal`）。両者を混同して「毎朝 `/goal` を起動する」設計にはしない —`/goal` は「今ある対象を片付けきる」単発の集中処理として、対象が発生した/たまったタイミングで起動する。
- **処理ログをローカルに残す** — 各ターンで「どの課題を、どう処理したか」を `state/burndown-log.md` に追記させる。EM が後から「無人実行中に何が起きたか」を振り返れるようにし、パターン2の `known-risks.json` と同様に「見えない自動処理」にしない。

## 構成イメージ

```
personal-pm-harness/
├── config/
│   ├── projects.yaml            # パターン1と共通
│   └── burndown-rules.yaml       # 対象ラベル・処理ルール・1ターンあたりの上限
├── state/
│   └── burndown-log.md           # 実行ごとの処理ログ（何件処理し、何が起きたか）
└── skills/
    └── backlog-burndown/
        └── SKILL.md               # 1件処理の手順（対象選定→処理→ログ記録→ラベル解除）
```

`config/burndown-rules.yaml` の例:

```yaml
targets:
  - name: needs-followup
    jql: "project in (PROJA, PROJB) AND labels = needs-followup"
    action: "担当者に3行以内で状況確認コメントを投稿し、labels から needs-followup を外して followed-up を付与する"
    maxTurns: 30

writeScope:
  allow:
    - "POST /rest/api/3/issue/{id}/comment"
    - "PUT /rest/api/3/issue/{id} (labelsフィールドのみ)"
  deny:
    - "ステータス遷移（Done化など）"
    - "アサイン変更"
```

## `/goal` 条件文の例

```
/goal 「project in (PROJA, PROJB) AND labels = needs-followup」のJQL検索結果が
0件になるまで、対象課題を1ターンにつき1件処理する。各ターンでは
(1) 検索結果の先頭1件を選ぶ、(2) config/burndown-rules.yaml の action に
従いコメントを投稿しラベルを付け替える、(3) state/burndown-log.md に処理内容を
1行追記する、の順に行う。ただし50ターンに達したら未処理分を残したまま停止する。
```

## 実行フロー

1. EM が対象バックログの発生を認識したタイミング（またはパターン2のアラートで「要フォローアップ」が一定件数を超えたタイミング）で、上記の `/goal` 条件をセッションに投げて起動する。
2. `/goal` が各ターン終了後に JQL 検索結果件数を判定し、0件になるまで自動でターンを継続する。
3. 各ターンの処理内容は `state/burndown-log.md` に追記され、EM は完了後（または途中経過を見たい時）にこのログを確認する。
4. エラー発生時は `/goal` 側の自動リトライ/一時停止に委ね、認証失効等の致命的エラー時のみ EM に通知が上がる。
5. 上限ターンに達して未処理分が残った場合は、次回起動時に同じ条件で再開する（残存件数は JQL が自動的に絞り込む）。

## 注意点・落とし穴

- **書き込み系アクションである以上、対象条件のJQLを緩めに書きすぎない** — パターン1/2は読み取り専用だったため誤りの影響が小さかったが、本パターンは実際に Jira へ書き込む。対象ラベルの条件を厳密にし、意図しない課題まで巻き込まないようにする。
- **1ターン1件を破らない** — まとめ処理をさせると、エラー発生時にどこまで処理済みかが分からなくなる。ログとJQLの再判定だけで「どこまで終わったか」が常に分かる設計を崩さない。
- **`/goal` は権限モードを変えない** — 無人で回すには auto mode 等との組み合わせが別途必要。Manual mode のままだと書き込み操作の許可プロンプトで止まり、無人運用にならない。
- **isolated worktree との相性を確認する** — Desktop scheduled tasks 経由で起動する場合、ローカルの未コミット変更を巻き込みたくないなら isolated worktree トグルを有効にする（[Desktop scheduled tasks の原文確認](../../research/01-official-features-for-personal-pm.md) §6 参照）。ただし本パターン自体はローカルリポジトリの変更を前提にしないため、通常は不要。
- **既定モデル変更によるコスト影響に注意** — Pro/Team Standard の既定モデルが Sonnet から Opus に変更された（`research/01-official-features-for-personal-pm.md` §8）。`/goal` はターンごとの判定に既定で小型モデル（Haiku）を使うが、判定後の本処理ターン自体は起動時のモデル設定に従うため、無人で回数を重ねる本パターンではコストが変わりうる。必要ならセッション起動時にモデルを明示指定する。
