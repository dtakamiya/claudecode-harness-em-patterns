# パターン1: 複数プロジェクトの進捗集約・自分用サマリ生成

## 課題

複数プロジェクト（複数リポジトリ、複数チーム）を掛け持ちする EM は、各プロジェクトの状況（PR の滞留、Issue の進捗、CI の状態、直近のコミット傾向）を毎朝/毎週、自分の頭の中で手作業で集約している。ソースが分散している（GitHub/GitLab、Jira/Linear、Slack）ため、集約コスト自体がボトルネックになり、後回しにされがちで、気づいたときには手遅れになる。

## ゴール

EM 本人だけが使う「自分専用のハーネス」に、担当プロジェクト一覧を定期的に自動で見に行かせ、要点だけをまとめたサマリを生成させる。チームへの展開は行わない（本人のワークフロー改善が目的）。

## 設計方針

- **横断先はリポジトリ単位の宣言的リストで持つ** — 対象プロジェクト（repo / board / チャンネル）を YAML や JSON で列挙し、追加・削除は設定ファイルの編集だけで完結させる。ハーネス本体のロジックに個別プロジェクト名をハードコードしない。
- **集約はサブエージェント並列 + 突合** — プロジェクトごとの調査は独立なので、プロジェクト数分のサブエージェントを並列 spawn して現状を集め、最後に1つの統合ステップで要約する。生ログはそのまま出力せず、統合済みサマリだけを最終成果物とする。
- **定期実行はスケジューラに委ねる** — 「毎朝」「毎週月曜」のような周期実行は cron（あるいは同等のスケジュール実行機能）に任せ、生成されたサマリを人間が読みに行く場所（チャットの通知、固定ファイル、ダッシュボード）に置く。手動で毎回起動しない。
- **差分ベースで書く** — 毎回ゼロから全件を洗うのではなく、前回サマリ（もしくは前回実行時刻）との差分に注目させる。変化がない項目は「変化なし」の一行で済ませ、変化があった項目に紙幅を割く。これによりサマリが「読めば数十秒で終わる」量に保たれる。
- **情報源ごとに読み取り専用アクセスに限定する** — このハーネスの役割は「見て要約する」ことであり、各プロジェクトへの書き込み（PRコメント、Issue更新など）は本パターンのスコープ外。誤操作のリスクを避けるため、権限は読み取り専用に絞る。

## 構成イメージ

```
personal-pm-harness/
├── config/
│   └── projects.yaml        # 追跡対象プロジェクトの宣言的リスト（repo, board, 通知先など）
├── cron/
│   └── jobs.json             # 毎朝/毎週の実行スケジュール定義
├── state/
│   └── last-summary.md       # 前回サマリ（差分比較の基準）
└── skills/
    └── progress-rollup/
        └── SKILL.md           # 集約〜要約の手順を書いたプレイブック
```

`config/projects.yaml` の例:

```yaml
projects:
  - name: project-a
    repo: org/project-a
    board: linear:PROJ-A
    watch: [open-prs, stale-issues, ci-status]
  - name: project-b
    repo: org/project-b
    board: github-issues
    watch: [open-prs, stale-issues]
```

## 実行フロー

1. cron が定期起動し、`progress-rollup` スキルを呼ぶ。
2. スキルが `config/projects.yaml` を読み、対象プロジェクトごとにサブエージェントを並列 spawn する。各サブエージェントは担当プロジェクトの PR/Issue/CI 状態を読み取り専用で取得する。
3. 各サブエージェントの結果を本体プロセスが受け取り、`state/last-summary.md` と突合して「新規に発生した変化」「解消した項目」「変化なし」に分類する。
4. 統合サマリを生成し、通知先（Slack DM、固定ファイル、ダッシュボード等）に出力する。生成後、`state/last-summary.md` を今回の内容で更新する。

## サマリのフォーマット例

```
## 進捗サマリ 2026-09-17

### 要対応（新規）
- project-a: PR #123 が2日レビュー待ち
- project-b: CI が3回連続失敗

### 進行中（変化なし）
- project-c: 予定通り

### 解消
- project-a: Issue #45 クローズ
```

## 注意点・落とし穴

- **サマリの粒度が肥大化しやすい** — 差分ベースにしないと、プロジェクト数が増えるごとに読む時間が線形に増え、結局読まれなくなる。「変化なし」を積極的に圧縮する設計を崩さないこと。
- **通知先の一本化** — サマリの出力先が分散すると「どこを見ればいいか」が曖昧になり、結局手動確認に戻ってしまう。1箇所（固定ファイル or 固定チャンネル）に集約する。
- **権限スコープを広げすぎない** — 「ついでに書き込みもできると便利」という誘惑があるが、本パターンは集約・可視化が目的。書き込み系のアクションは別パターン（意思決定支援や委譲管理）に切り出す。
